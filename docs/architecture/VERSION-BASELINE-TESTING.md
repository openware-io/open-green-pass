# 版本基线驱动的测试资产治理

## 决策

GreenPass 不建设第二个源码仓库。GitHub、GitLab 等 SCM 是源码唯一事实来源；平台围绕不可变版本基线管理分析、用例、执行、证据与审计。

一个版本基线至少由以下信息组成：

```text
仓库地址 + commit SHA + 服务目录 + 技术画像版本
+ 解析器版本 + 模型/提示词版本
+ 环境基线（镜像 digest、契约、测试数据、特性开关）
```

分支只用于任务启动时选择入口。Worker 必须先将分支解析为 commit SHA；分支后续移动不能改变既有生成、审核或执行记录。

## 架构与数据边界

```text
SCM webhook / 补偿扫描
        │（验签、幂等、乱序处理）
        ▼
版本基线与影响分析 ──► 增量候选生成 ──► 人工审核 ──► 用例版本库
        │                     │                         │
        ▼                     ▼                         ▼
临时受控源码上下文       文件清单/内容哈希             分层回归编排
        │                     │                         │
        └──────────────► 证据与可信审计链 ◄──────────────┘
```

- **SCM 接入层**：使用 GitHub App 安装令牌或 Fine-grained PAT；只允许读取授权仓库的 Metadata 和 Contents。令牌存储在服务端 Secret，禁止经前端、请求参数、审计载荷或日志传递。
- **临时源码上下文**：只读当前服务目录内受限的文本文件，排除密钥、依赖目录和构建产物；分析/生成完成即清除正文，不使用持久化工作目录，不克隆完整仓库。
- **证据库**：长期保存 commit SHA、目录、文件路径清单、内容哈希、解析器/模型/提示词版本、影响结论、用例版本、执行环境和结果哈希；默认不长期保存源码正文。
- **加速缓存**：如果启用，必须是可丢弃的内容寻址缓存，按文件哈希去重，设置容量上限、TTL、LRU 淘汰和命中率监控。缓存不是审计事实，清空后必须可从 SCM 同一 commit 重新构建。
- **例外归档**：仅在法律取证、争议复现或 SCM 留存无法满足要求时，经审批将最小源码片段加密归档；归档应具备 TTL、访问控制、密钥轮换与下载审计。

## 代码持续迭代

每个新 commit 都形成候选基线，而不是覆盖旧基线。影响分析综合 Git diff、依赖图、路由、接口契约、数据库迁移、需求/页面/用户旅程追溯和历史失败数据，分为未受影响、需回归、需更新、新增能力和废弃建议。

当前产品阶段只对用户维护一份“当前有效用例”，不提供用例多版本选择。发起一次生成即创建一次迭代：用户只选择本次分支或 Tag，服务端自动以同项目、仓库、服务最近一次**已生效**批次为基线（没有则为首次生成），并拒绝客户端传入基线编号。审核通过后，稳定逻辑 ID 对应的用例被新增或更新，基线中未覆盖的用例归档；执行与默认用例列表只读取 `active` 用例。`cas_version` 仍只作为不可篡改的审计与回溯记录，不能被当作日常多版本用例库操作。

增量回归不能取代系统保障：每次变更至少运行冒烟和关键链路；中高风险变更扩大到契约/权限/跨服务回归；发布 tag 或风险阈值触发全量或风险驱动回归。超过提交数、时间或风险阈值未处理的基线必须重新分析，避免增量积压失真。

## 执行环境确认模型

运行中的系统（例如 kind 内的 `pc-admin`）不是 GreenPass 的部署对象。平台只登记并验证测试将连接的目标环境，且把环境事实与 AI 推断严格分开：

```text
技术画像 + 用例类型 + 源码证据
            │
            ▼
    待确认环境需求清单（AI 建议）
            │ 用户/管理员填入真实环境信息
            ▼
 环境模板 + 运行时参数 + 连通/权限预检
            │
            ▼
  不可变执行环境基线 ──► 测试编排与可信审计
```

环境登记必须由用户显式确认。平台保存环境名称、HTTP(S) origin、运行版本、浏览器/测试数据配置以及需求依据；账号只保存密钥管理器的**凭据引用名**，绝不保存密码、Token、Cookie 或私钥。任一需求未确认时，创建真实运行必须阻断。

对 Web 应用，画像默认提出入口地址、运行版本、测试账号凭据引用、浏览器配置、测试数据上下文五项；对 API 服务，至少提出 origin 与运行版本。每项必须显示 AI/规则的推断理由和源码证据，用户可修改真实值但不能把推断当事实。

环境基线与代码 commit、用例版本、浏览器/Runner 镜像、测试数据版本一并记录。执行前进行 URL、版本、登录/权限和依赖预检；预检无法确定时显式阻断或降级。HTTP Runner 只能执行声明式 API 用例；Web UI 用例必须由受管浏览器 Runner 执行，禁止以 HTTP 冒烟伪装 UI 通过。

## 可复现性与容量治理

复现时重新从 SCM 拉取相同 commit，并逐项校验文件哈希。SCM 不可用时系统只能声明“可审计、暂不可复现”，不能伪造复现成功。

正文清除后仍可通过 commit、文件清单、内容哈希、生成输入版本和输出哈希证明生成依据。关键发布基线要求受保护分支或 tag；对可能被 force-push、删除、LFS 或子模块失效的来源，在任务创建时预检并在必要时走受审批加密归档。

容量指标至少包含：临时区峰值、缓存占用/上限、TTL 回收率、引用阻塞、缓存命中率、SCM 回源失败率和令牌限流率。达到上限时停止写入可选缓存并告警，不删除仍被合规归档引用的证据。

## 当前实现与后续工作

当前生成管道已实施以下基础能力：限制读取文件数/大小、冻结 commit、保存文件清单与内容哈希、模型结构化候选与确定性质量门；质量门完成后自动清除数据库中的源码正文，仅保留可审计证据包。`GP_GITHUB_READ_TOKEN` 可由服务端 Secret 注入 Worker，缓解匿名 GitHub API 限流。

后续按优先级实施：

1. GitHub App 安装令牌与 token 轮换，替代长期 PAT；SCM webhook 验签、事件水位和补偿扫描。
2. 基线、文件证据、影响分析和用例逻辑 ID 的独立持久化模型；增加基线详情与容量治理界面。
3. 依赖/契约/用户旅程驱动的风险分级影响分析，支持多仓库系统基线。
4. 临时执行工作区或受管浏览器 Runner；Web UI 用例不以 HTTP 用例冒充。
5. 内容寻址缓存、对象存储加密归档、TTL/配额/回收任务与监控告警。

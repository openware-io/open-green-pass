# 自动生成与执行闭环实施方案

## 目标

形成一条真实、可追踪且不会把模型输出当作可执行代码的流程：

```text
已确认的服务目录 + 仓库分支
  -> 固定源码版本并保存受限快照
  -> 解析 OpenAPI / 源码证据
  -> 模型生成结构化候选用例
  -> 确定性校验与去重
  -> 人工审核
  -> 事务性写入用例库并记录用例 ID
  -> 从生成批次选择已入库用例
  -> 进入执行页，配置测试环境并创建 Run
  -> 现有 Temporal 执行流程完成版本校验、执行、结果与证据
```

## 边界与安全

- 首期读取公开 GitHub 仓库；仅读取所选服务目录内受限数量和大小的文本文件，不克隆仓库、不读取密钥文件、不把用户提供的 URL 当作任意网络目标。
- 每个批次固定 Git commit SHA，并保存输入文件、哈希及解析摘要，模型重试不会悄悄换用后续提交。
- 模型只可返回结构化 HTTP/API 用例规格（请求方法、相对路径、允许的请求头、JSON 请求体和断言）；严禁模型生成 shell、任意命令或任意 URL。
- 质量门是确定性校验：格式、方法/路径、断言、大小限制和重复检查。失败或无法验证的候选不允许标记通过或写入正式用例。
- 正式用例仅在审核后事务性入库；每条种子保存对应 `case_id`，执行范围精确限定为本批次用例。
- 执行时只使用管理员登记的环境地址；测试请求的目标主机不来自模型输出。执行容器无服务账号令牌、非 root、只读根文件系统，结果由现有执行域落库和生成证据哈希。
- 首期可执行范围是 API/HTTP 合约用例。交互式浏览器 E2E（Playwright、登录态、截图）需单独接入受管浏览器 Runner，不用 HTTP 冒烟冒充 UI 测试。

## 实施顺序

1. **生成输入与批次**：源码冻结、快照、OpenAPI 解析、结构化生成、多条种子幂等写入。
2. **质量与审核**：静态校验和去重、显示完整用例内容、记录审核人/决策/请求 ID、接可信审计链。
3. **正式入库**：只提交质量通过的种子；写用例主体/版本和种子映射同事务完成，支持重复活动重试。
4. **进入执行**：批次审批完成后提供“执行本批用例”，跳转现有执行页并预选对应 case IDs；不在模型对话中绕过用户确认直接执行。
5. **真实执行**：环境登记运行版本与 Base URL；Run 只使用本批次 case IDs，由 Temporal 按现有版本校验和执行流程跑完并显示结果/证据。
6. **验证**：先覆盖源码读取、解析、结构化候选校验、质量拦截、审核与执行规格单测；再跑后端/前端检查；最后在本地隔离环境做一次人工确认的端到端运行。模型不可用、源不可读、环境未配置时必须明确失败，不产生假通过。

## 完成判据

- 新建批次后，能够看到实际源码 SHA、来源文件和非空结构化候选；无证据/无效输出会失败。
- 未审核或质量未通过的种子不能进入 `cas_case` / `cas_version`。
- 审核通过后每条种子都能追到正式用例 ID，重复工作流不会产生重复用例。
- 批次页可将本批次用例精确带入执行页；Run 范围、环境版本校验、实际执行结果和证据可回查。
- Mock Runner 不得被展示为真实通过；未配置真实执行器或环境时，页面说明阻塞原因。

# GreenPass · 软件工程测试治理平台 — 产品需求文档（PRD）

> 文档状态：**持续维护中（随原型迭代同步更新）**
> 最后更新：2026-09-26
> 定位：本 PRD 是产品需求的唯一权威来源，原型工程 `open-qa` 的每一次迭代都必须在此同步记录需求演进与落地情况。

---

## 1. 产品定位

**一句话定位**：面向**中大型技术团队**的**软件工程测试治理平台**——站在软件工程"测试阶段"的位置，对（AI 生成 / 人写的）被测工程与系统做**质量量化、测试管控与可信治理**；系统本身由 AI 驱动（用例生成、质量判定、契约分析、篡改检测等）。

**两个关键属性（互不矛盾）**：
- **通用测试定位**：AI 生成的系统能测，人开发的软件系统同样能测——平台不局限于"只测 AI 产物"，而是覆盖所有进入测试阶段的工程。
- **AI 驱动实现**：平台的生成、判定、分析能力由 AI 模型提供，并且**每个工程可自行选择使用的 AI 模型**。

**命名**：GreenPass（绿牌放行），寓意"测试通过、质量过关"。

## 2. 目标用户与规模假设

| 维度 | 说明 |
|---|---|
| 目标客户 | 中大型技术团队（多小组 / 多产品线并行） |
| 使用形态 | 团队级协作 + 多租户数据隔离 |
| 角色规模 | 一个团队数十名成员，支持按团队切分管理 |
| 部署形态 | SaaS / 私有化（原型阶段不限定） |

## 3. 核心需求一览

### 3.1 多租户团队切分（团队即租户）
- **需求点 R-ORG-1**：一套账号体系下支持**多个团队**并存，团队之间**数据完全隔离**（工程、用例、契约、门禁、审计各自独立）。
- **需求点 R-ORG-2**：支持**切换当前团队上下文**，切换后各页面展示的数据均为该团队范围内的结果。
- 落地现状：新增「团队与权限」页，提供团队卡片列表与切换交互（mock 示意）；顶栏展示当前团队标识。

### 3.2 团队内人员管理
- **需求点 R-ORG-3**：团队内可进行**成员管理**——添加 / 邀请成员、调整成员角色、停用成员、查看活跃状态。
- **需求点 R-ORG-4**：提供**角色体系**（团队所有者 / 管理员 / 测试工程师 / 只读成员），并有清晰的**角色权限矩阵**。
- **需求点 R-ORG-5（资产级权限，可分配）**：研发组内不同成员对**资产树中不同资产**的权限应可分配，而非全局统一。
- **需求点 R-ORG-6（工程负责人）**：每个资产设一名**工程负责人**，持有该资产的**完整权限**；负责人可对成员做该资产的**权限与资源精细分配**（权限级别 + 并发/沙箱配额）。
- 落地现状：「团队与权限」页含成员表格（角色下拉可切换、状态徽标）+ 角色权限矩阵（能力点 × 角色）+ **资产权限分配板块**（按资产点选 → 工程负责人完整权限 → 成员权限下拉 + 并发/沙箱配额）。

### 3.3 每个工程可选 AI 模型（模型即配置）
- **需求点 R-MODEL-1**：提供**模型池**（多个可用 AI 模型，如豆包 / DeepSeek / GPT / Claude / 私有化自研），团队级可见可用。
- **需求点 R-MODEL-2**：**每个工程（被测对象）独立绑定**测试所用的 AI 模型，可按工程覆盖全局默认模型。
- **需求点 R-MODEL-3**：模型池支持**接入新模型**（API Key / 私有化）与**设置默认模型**。
- 落地现状：新增「AI 模型配置」页（模型池卡片 + 每工程模型绑定表 + 接入/默认按钮）；「被测对象画像」主卡展示当前工程绑定的测试 AI 模型。

### 3.4 测试治理主链路（既有核心需求，随原型持续完善）
| 需求点 | 说明 | 对应页面 |
|---|---|---|
| R-TEST-1 | 被测对象画像：质量评分构成、AI 生成过程还原、资产风险明细 | 被测对象画像 |
| R-TEST-2 | 上游源接入与用例生成管道（六类上游源 → 适配器 → 种子 → 质量验证） | 上游源与生成 |
| R-TEST-3 | 测试用例库（版本化、断言强度、变异分数、上游绑定） | 测试用例库 |
| R-TEST-4 | 测试执行（实时进度、证据捕获、不放水不跳过） | 测试执行 |
| R-TEST-5 | 契约测试（注册表、变更影响、消费者验证） | 契约测试 |
| R-TEST-6 | 质量门禁（策略即代码、AI 判定、篡改检测、契约门禁、可重新判定） | 质量门禁 |
| R-TEST-7 | 审计日志（哈希链、仅追加、可独立验证） | 审计日志 |
| R-TEST-8 | 需求追溯矩阵（跨服务追溯链） | 需求追溯 |
| R-TEST-9 | 并发与资源（调度、隔离、资源池、冲突） | 并发与资源 |
| R-TEST-10 | 成本审计：AI 场景成本总览与明细（关联到每次用例生成、每个用例执行；存量执行成本持平或递减） | 审计管理 · 成本审计 |
| R-TEST-11 | 测试历史：以「测试运行(Run)」为时间维主键，运行列表 / 通过率趋势 / 运行详情（执行明细 · 服务报告 · 测试证据 · 用例成本） | 测试历史 |
| R-TEST-12 | 测试证据：按「用例→Run」组织，截图证据为普遍规范 + 服务级开关，sha256 哈希锚定审计链 | 测试历史 |
| R-TEST-13 | 截图证据策略：服务级可单独关闭（如 mobile-android），防高并发 / 大流量服务截图性能开销 | 测试历史 |
| R-REPORT-10 | 测试报告「查看 + 导出」：HTML / PDF / Word / Markdown 四格式 | 测试报告 |
| R-REPORT-11 | 报告分级下钻：工程 → 服务 → 用例 三级，每级独立导出（文件名分级 RUN-4821 / -svc-payment / -TC-2024-095） | 测试报告 |
| R-REPORT-12 | 测试报告为**测试闭环最后一环**：独立菜单页 /report，含运行选择器，闭环定位（画像→…→测试历史→测试报告） | 测试报告 |

> 成本审计（R-TEST-10）设计要点：所有用到 AI 的场景，在 AI 允许的前提下，把当前操作的成本数据（模型、Token 输入/输出、金额）关联回来；成本由**单价表 × token 量**统一计算（`aiCost` 函数派生），总览 = 各明细之和，保证口径一致不混乱。形态：**总览**（总成本 / Token 总量 / 调用次数 / 平均每用例成本）+ **成本趋势**（总成本波动、存量执行成本持平或递减）+ **场景成本占比** + **明细双表**（用例生成成本、用例执行成本，每条关联用例 ID / 触发源 / 模型 / Token / 金额）。

## 4. 权限体系设计（R-ORG-3 / R-ORG-4 详述）

### 4.1 角色定义
| 角色 | 定位 | 权限要点 |
|---|---|---|
| 团队所有者 owner | 团队最高权限 | 团队 / 席位 / 账单管理 |
| 管理员 admin | 运营管理者 | 成员、工程、模型、门禁策略 |
| 测试工程师 tester | 一线执行 | 用例创建执行、风险处理、重新判定 |
| 只读成员 viewer | 审计 / 查看 | 仅查看结果与审计，不可变更 |

### 4.2 权限矩阵（能力点 × 角色）
| 能力点 | owner | admin | tester | viewer |
|---|---|---|---|---|
| 团队与席位管理 | ✓ | ✕ | ✕ | ✕ |
| 成员与角色管理 | ✓ | ✓ | ✕ | ✕ |
| 工程 / 模型配置 | ✓ | ✓ | ✕ | ✕ |
| 门禁策略编辑 | ✓ | ✓ | ✕ | ✕ |
| 用例创建与执行 | ✓ | ✓ | ✓ | ✕ |
| 风险处理 / 重新判定 | ✓ | ✓ | ✓ | ✕ |
| 查看结果与审计 | ✓ | ✓ | ✓ | ✓ |

> 说明：原型阶段权限矩阵为静态展示；后续可做"按角色渲染操作按钮 / 入口"的动态权限控制。

### 4.3 资产级权限分配（R-ORG-5 / R-ORG-6）

团队角色决定成员"在团队内能做什么"，**资产权限**决定成员"能操作哪些资产、以及在该资产上做到什么程度"。两者叠加。

| 资产权限 | 含义 | 是否可再分配 |
|---|---|---|
| full 完整 | 等同于工程负责人，可对该资产再分配权限与资源 | 是 |
| edit 编辑 | 创建 / 修改用例与门禁判定 | 否 |
| exec 执行 | 运行用例、查看执行证据 | 否 |
| view 只读 | 仅查看该资产结果与审计 | 否 |
| none 无权限 | 对该资产不可见、不可操作 | 否 |

- **工程负责人**：每个资产持有一名负责人，默认拥有 `full` 完整权限，负责该资产成员权限与资源（并发执行配额、K8s 沙箱配额）的精细分配。
- **分配粒度**：成员 × 资产 ×（权限级别 + 资源配额），配额按成员独立生效。
- **与团队隔离的关系**：资产权限分配在**当前团队上下文内**生效，团队间数据隔离不变。
- 落地现状：「团队与权限」页新增"资产权限分配 · 按资产精细管控"板块（原型以 mock 示意）。

## 5. AI 模型体系设计（R-MODEL 详述）

- **模型池**：团队级维护一个可用模型列表，每条含名称、厂商、能力、成本、时延、标签、是否默认。
- **工程绑定**：`被测对象(工程) → 模型` 一对一绑定，绑定后可覆盖团队默认模型；画像页主卡展示当前绑定。
- **默认机制**：团队可设一个默认模型，未显式绑定的工程默认使用该模型。
- **接入 / 治理**：支持新增模型（API Key 或私有化部署）；企业级需合规审批（原型示意）。

---

## 6. 数据隔离与多租户说明（R-ORG-1 / R-ORG-2）

- 数据维度：工程、用例、契约、门禁、审计均按**团队**隔离。
- 原型现状：以 mock 数据 + 团队上下文切换示意；真实后端需按 `team_id` 做租户隔离与鉴权。
- 后续演进方向：跨团队共享基线、团队级配额、操作审计留痕按团队归属。

---

## 7. 边界与约束（原型阶段）

- **只做前端原型工程**：所有数据为 mock（`src/data/mock.ts` 单一数据源，派生指标从明细现算，保证跨页自洽）。
- **不做后端业务**：交互（重新判定、搜索、成员/模型配置等）均为前端 mock 反馈，不接真实服务。
- **可独立打开**：原型以 React+Vite 构建，产出单文件 `GreenPass-standalone.html`，`file://` 双击即用（HashRouter 兼容静态打开）。
